<a name="bug-01"></a>
## BUG-01 — Фильтр по `checkin` не возвращает созданную бронь

**Severity:** Major · **Priority:** High · **Эндпоинт:** `GET /booking`

### Описание
При фильтрации списка бронирований по параметру `checkin` в ответе отсутствует бронь, созданная непосредственно перед запросом с этой же датой заезда. Фильтр по `checkout`, `firstname` и `lastname` при этом работает корректно.

### Предусловия
1. Тестовый стенд доступен.
2. Выполнен `POST /booking`, получен валидный `bookingid`.

### Шаги воспроизведения
1. Отправить `POST /booking` с валидным телом запроса.
2. Сохранить из ответа `bookingid` и значение `bookingdates.checkin`.
3. Отправить `GET /booking?checkin={сохранённая_дата}`.

### Ожидаемый результат
`200 OK`, массив ответа содержит объект с сохранённым `bookingid`.

### Фактический результат
`200 OK`, сохранённый `bookingid` в массиве отсутствует.

### Дополнительно
- Воспроизводится также при комбинации `checkin` + `checkout` и при запросе со всеми фильтрами одновременно.
- Одиночные фильтры `firstname`, `lastname`, `checkout` работают корректно.
- Дефект плавающий по проявлению в общем массиве данных, но проверка на присутствие собственной брони падает стабильно.

<a name="bug-02"></a>
## BUG-02 — 500 Internal Server Error при невалидном формате даты в query-параметре

**Severity:** Major · **Priority:** High · **Эндпоинт:** `GET /booking`

### Описание
Передача строки, не соответствующей формату даты, в query-параметр `checkin` или `checkout` приводит к необработанному исключению на сервере вместо ответа с ошибкой валидации.

### Предусловия
Тестовый стенд доступен.

### Шаги воспроизведения
1. Отправить `GET /booking?checkin=invalid-date`.
2. Повторить с `GET /booking?checkout=invalid-date`.

### Ожидаемый результат
`400 Bad Request` с сообщением об ошибке формата даты, либо `200 OK` с пустым массивом.

### Фактический результат
`500 Internal Server Error`, тело ответа: `Internal Server Error`.

<a name="bug-03"></a>
## BUG-03 — 500 Internal Server Error при передаче числа в поле `firstname`

**Severity:** Major · **Priority:** High · **Эндпоинт:** `PUT /booking/:id`

### Описание
При полном обновлении брони с числовым значением в строковом поле `firstname` сервер падает с необработанным исключением вместо возврата ошибки валидации типа.

### Предусловия
1. Тестовый стенд доступен.
2. Получен валидный `authToken` через `POST /auth`.
3. Выполнен `POST /booking`, получен валидный `bookingid`.

### Шаги воспроизведения
1. Отправить `PUT /booking/{bookingid}`.
2. Заголовки: `Content-Type: application/json`, `Cookie: token={authToken}`.
3. Тело запроса — валидный JSON, но поле `firstname` передано числом:
```json
{
  "firstname": 12345,
  "lastname": "Brown",
  "totalprice": 111,
  "depositpaid": true,
  "bookingdates": { "checkin": "2018-01-01", "checkout": "2019-01-01" },
  "additionalneeds": "Breakfast"
}
```

### Ожидаемый результат
`400 Bad Request` с сообщением об ошибке валидации типа (ожидается строка).

### Фактический результат
`500 Internal Server Error`.

<a name="bug-04"></a>
## BUG-04 — Отсутствует валидация тела запроса при обновлении брони

**Severity:** Major · **Priority:** High · **Эндпоинты:** `PUT /booking/:id`, `PATCH /booking/:id`

### Описание
Оба метода обновления принимают данные с нарушением типов и бизнес-логики, возвращают `200 OK` и сохраняют некорректные значения в брони. Валидация входных данных отсутствует.

### Предусловия
1. Тестовый стенд доступен.
2. Получен валидный `authToken` через `POST /auth`.
3. Выполнен `POST /booking`, получен валидный `bookingid`.

### Шаги воспроизведения
1. Отправить `PUT` или `PATCH` на `/booking/{bookingid}` с валидной авторизацией.
2. В теле запроса передать одно из значений из таблицы ниже.
3. Проверить код ответа.

### Проверенные варианты

| Поле | Переданное значение | Метод | Ожидаемо | Фактически |
|------|---------------------|-------|----------|------------|
| `firstname` | `""` (пустая строка) | PUT | 400 | **200** |
| `lastname` | `""` (пустая строка) | PUT | 400 | **200** |
| `additionalneeds` | `""` (пустая строка) | PUT | 400 | **200** |
| `totalprice` | `"сто рублей"` (строка) | PUT, PATCH | 400 | **200** |
| `lastname` | `100` (число) | PATCH | 400 | **200** |
| `depositpaid` | `"yes"` (строка) | PUT, PATCH | 400 | **200** |
| `totalprice` | `-500` | PUT, PATCH | 400 | **200** |
| `bookingdates` | `checkout` раньше `checkin` | PUT, PATCH | 400 | **200** |
| `bookingdates` | формат `DD.MM.YYYY` | PUT | 400 | **200** |

### Ожидаемый результат
`400 Bad Request` с описанием ошибки валидации.

### Фактический результат
`200 OK`, некорректное значение записывается в бронь.

### Дополнительно
Обязательность полей при этом проверяется: отсутствие `firstname`, `lastname`, `totalprice`, `depositpaid` или `bookingdates` в `PUT` корректно возвращает `400`. То есть реализована проверка наличия полей, но не проверка их содержимого.

<a name="bug-05"></a>
## BUG-05 — 405 Method Not Allowed вместо 404 Not Found при несуществующем `bookingid`

**Severity:** Medium · **Priority:** Medium · **Эндпоинты:** `PATCH /booking/:id`, `DELETE /booking/:id`

### Описание
Обращение к несуществующему идентификатору брони возвращает `405 Method Not Allowed`. Этот код означает, что HTTP-метод не поддерживается ресурсом, тогда как метод поддерживается, а отсутствует сам ресурс. Корректный ответ — `404 Not Found`.

### Предусловия
1. Тестовый стенд доступен.
2. Получен валидный `authToken`.
3. Идентификатор `12312321313` заведомо отсутствует в базе.

### Шаги воспроизведения
1. Отправить `PATCH /booking/9999999999` с валидной авторизацией и телом `{"firstname": "Test"}`.
2. Отправить `DELETE /booking/12312321313` с валидной авторизацией.

### Ожидаемый результат
`404 Not Found`.

### Фактический результат
`405 Method Not Allowed`, тело ответа: `Method Not Allowed`.

### Дополнительно
`GET /booking/:id` с несуществующим идентификатором при этом корректно возвращает `404`. Дефект затрагивает только методы изменения и удаления.
